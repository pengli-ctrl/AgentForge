# AgentForge · P1-1 负载压测与容量估算报告

> 日期：2026-01-15 · 分支：`main`
> 场景：企业 SME 客服 AI 平台（FastAPI + 事件驱动架构）· 单机本地压测
> 关键词：真实压测 / 容量估算 / GitHub 亮点资产

## 0. TL;DR

| 指标 | 数值 |
|---|---|
| 平台 API 峰值吞吐 | **~580–630 rps**（多进程客户端测得） |
| 安全工作点（P90 延迟 < 50ms） | **~500 rps**（10 并发/进程 4） |
| 5 秒延迟预算（P99 < 5s） | 并发 ≤ 50 |
| 推荐接入并发 | **≤ 25**（RPS ~480–570，P90 < 750ms） |
| 最优并发点 | 10（P90 ≈ 47ms，吞吐 ~520–580 rps） |
| 单 worker 服务端能力（估算） | ~600 rps（受限于本机环回 I/O + uvicorn 单进程） |
| 扩展方式 | 多 worker 不受益于本机压测环境（详见 §5） |

**结论**：平台在单机、零外部依赖（内存容器 + 真实聚合逻辑）下具备 **~500 rps / 25 并发** 的稳定服务能力；峰值 ~600 rps。对 SME 客服中台（会话量通常 < 50 rps）留有 **10 倍以上** 余量。

## 1. 目标与方法

### 1.1 目标
1. 给出平台 API 在真实请求下的**吞吐与延迟画像**（非空转框架基线）。
2. 形成**容量估算**：单节点在可接受延迟下的最大承载，用于回答"这套平台能撑多少客服会话"。
3. 全部**本地、可复现、零外部依赖**，可直接放 GitHub 复跑。

### 1.2 为什么不用 k6 / locust（自研压测器的动机）
- 目标环境是**离线/内网** SME 交付，安装 k6/locust 增加依赖。
- 自研压测器（`bench/loadgen.py`）基于已随项目安装的 `httpx + asyncio`，**零新增依赖**，可复现。
- 关键教训：压测器自身也会成为瓶颈（详见 §2），因此实现了**多进程负载生成**。

### 1.3 被测对象与端点
启动 `bench/platform_bench_app.py`（内存容器 + 预置配额/成本/工单数据，关闭鉴权、零外部服务）。
选取三个代表性端点覆盖"框架基线 → 业务读 → 聚合读"三档：

| 端点 | 类型 | 说明 |
|---|---|---|
| `GET /health/live` | 纯框架基线 | 近零业务逻辑 |
| `GET /v1/console/overview?tenant_id=tenant-a` | 业务读 | 配额 + 成本多仓库读取 |
| `GET /v1/console/dashboard?tenant_id=tenant-a` | 聚合读 | 成本趋势 + 模型分布计算 |

### 1.4 压测配置
- 负载生成器：4 个子进程，每进程按 clients/4 并发，独立 httpx 连接池 + 各自事件循环。
- 并发梯度：1 / 10 / 25 / 50 / 100。
- 每梯度持续时间：8 秒。warmup：2 秒。
- 指标：吞吐 req/s、P50/P90/P95/P99 延迟、错误率。

## 2. 关键方法学发现：压测器自身是瓶颈（必须先排除）

单进程负载生成器的最大陷阱：**asyncio + httpx 客户端在同一进程内受 GIL / 单事件循环限制，客户端吞吐封顶，会掩盖服务端真实容量。**

实测验证（`GET /health/live`，目标服务单 worker）：

| 压测器形态 | 实测吞吐 |
|---|---|
| 单进程 50 并发 | ~73 rps |
| 单进程 1 并发（背靠背） | ~190 rps |
| 4 进程 × 15 并发 | **~260 rps** |
| 8 进程（多组并发） | ~600–630 rps |

**解释**：单进程客户端在多核机器上用不了多核（GIL），把所有并发压在同一事件循环，客户端先饱和。这会导致**任何服务端**看起来都只有 ~75–190 rps，误判为"服务端容量低"。

**结论**：压测必须用**多进程客户端**（与 k6 的多 worker 同思路）。本报告吞吐数据均来自多进程负载生成器。

## 4. 容量估算

### 4.1 观察
1. **吞吐峰值出现在 10 并发**（~520–580 rps），随后随并发下降：25 并发仍 ~540，50 并发跌到 ~360，100 并发 ~190。这是典型**服务端在过载后吞吐回落**（队列积压 + 排队延迟）。
2. **延迟与并发强相关**：P99 从 10 并发的 <80ms → 25 并发的 ~1.5s → 50 并发的 ~4s。**服务端是单 worker 单事件循环**，高并发下请求串行化排队。
3. 峰值 ~600 rps 与 8 进程客户端、320 并发的实测一致，说明**本机物理上限 ~600 rps**（环回 I/O + uvicorn 单进程 + Windows 网络栈共同作用）。

### 4.2 三种服务等级下的容量

| 等级 | 约束 | 建议并发 | 对应吞吐 |
|---|---|---|---|
| 稳定（最优延迟） | P90 < 50ms | ≤ 10 | **~520–580 rps** |
| 平衡（业务可用） | P90 < 750ms | ≤ 25 | **~490–570 rps** |
| 极限（短时支撑） | P99 < 5s | ≤ 50 | **~360–420 rps** |

### 4.3 单节点容量结论
- **单节点推荐承载：≤ 25 并发、~500 rps**，P90 延迟 < 750ms，符合一般后台 API 可用性目标。
- 峰值能力 ~600 rps，短时突发可扛到 50 并发（P99 < 5s）。
- 对 SME 客服平台：即使假设一批客服会话高峰 50–100 rps，本节点 500 rps 能力仍留有 **5–10 倍**余量。

### 4.4 水平扩展提示
- 本环境压测受**单 worker** 限制。生产建议按需提升 worker/副本数或引入负载均衡，从而将对单进程的并发需求分摊。多 worker 的收益需在**多核生产环境**下复测（本压测机的 Windows 单进程环境体现不出多 worker 提升，见 §5）。

## 5. 多 worker 专项测定（重要）

用相同多进程客户端对比 `--workers 1` 与 `--workers 4` 的峰值吞吐：

| workers | 峰值 rps（8 进程 × 10 并发） |
|---|---|
| 1 | 632 |
| 4 | 596 |

**关键发现**：本机 4 worker 未带来吞吐提升（596 vs 632）。这不是"多 worker 无效"，而是**本压测机的物理上限**已达 ~600 rps：
- 压测器 8 进程 × 10 并发 = 80 并发已达客户端 + 环回带宽饱和。
- 进一步把进程/并发翻倍（4×40、8×40），吞吐不升反微降（614）→ 机器/环回已到顶。
- Windows 上 uvicorn `--workers` 需 `--factory` 配合独立事件循环构建方可启动（spawn + asyncio 冲突坑，已在 `platform_bench_app.py` 解决）。

**推论**：
- 单进程（单 worker）在**当前压测机**上即可到 ~600 rps，说明平台代码本身不是高并发瓶颈。
- 生产要突破单进程上限，应上**多 worker / 多副本 + 负载均衡**，并在 **Linux 多核生产环境**复测（本机为 Windows 单机，无法隔离展示多核扩展性）。

## 6. 复现

```bash
# 1) 安装依赖（仅项目已有依赖，无新增）
pip install -r requirements.txt -r requirements-dev.txt

# 2) 一键压测（默认 8s/梯度，5 级并发；可传秒数）
cd <repo>
python bench/run_bench.py 8

# 3) 产物
#    - bench/results_{health,overview,dashboard}.json  原始数据
#    - 控制台打印各端点各并发梯度的 吞吐/延迟分位/错误率
```

> 说明：`bench/run_bench.py` 用 uvicorn 启动内存容器 bench 应用（零外部服务），开 4 个多进程客户端压测 3 个端点。全部本地回环，无需公网。

## 7. 局限与后续

- **本报告为单机基准**，反映代码路径与单节点单 worker 能力；未覆盖跨服务（Postgres/Temporal/MinIO）的真实 I/O 成本（生产会引入落库等开销，吞吐会降低）。
- **未测写路径**（如释放门禁、事件出站批量写）；后续可按需补 `POST /v1/release/gate` 等。
- **建议**：生产部署后用 Linux 多核环境复测多 worker，验证线性扩展；并在真实依赖栈（Postgres 等）下复核容量。
- 修复了压测器单进程瓶颈（多进程化），这是本任务方法论上的关键产出，避免了对服务端容量的严重低估。
